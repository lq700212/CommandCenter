# 相机判定"NG 被报成 OK"修复方案（响应错位 + 判定字段健壮性）

> 方案日期：2026-08-15
> 对象文件：`CommandCenter/Services/KeyenceIV4Camera.cs`
> 问题现象：PLC 反馈"相机拍照判定为 NG，上位机写过去的 PLC 结果却是 OK(1)"
> 状态：**方案评审中（未实施）**——本文档先沉淀诊断结论与改法，确认后再动代码

---

## 一、问题现象

现场（Z121，上/下各 1 台基恩士 IV4-500CA）反馈：

- 相机实拍判定 NG，但 PLC 收到的相机结果却是 **1=OK**；
- 界面/存图路径（`E:\Images\...\上相机\OK\`）也能看到本应进 NG 目录的图片；
- 这意味着**不良品可能被放行**，属于必须优先处理的质量风险。

初步判断不是"解析规则出错导致一切皆判 OK"（那样会 100% 复现、全 NG 全放行），
而是**偶发性的响应错位**——问题恰恰在于"偶发"更危险、更隐蔽。

---

## 二、现场日志证据（`运行日志_20260815.log`）

**结论先行：高频触发时段，相机指令与回帧严重错位（上位机收到的回帧不是本条指令的应答）。**

| 时间 | 上位机发的指令 | 读到的回帧 | 证据意义 |
| --- | --- | --- | --- |
| 18:26:08 | 点位14 发 `PW,019`（切程序） | `RT,02840,NG,01,NG,0000000` | PW 指令读回的是上一拍 **T2 的残留 RT 帧** |
| 18:26:14 | 点位15 发 `T2`（触发+判定） | `PW` | T2 读回的是上一拍 **PW 的残留回显** |
| 18:26:39 | 点位18 发 `PW,022` | `RT,02911,**OK**,01,OK,0000100` | **最危险**：PW 读回的是上一拍 T2 的 **OK** 残留帧 |
| 18:26:57 | 点位21 发 `PW,024` | `ER,T2,03` | 连错误帧都串位了 |
| 18:27:00 | 点位22 发 `PW,025` | `RT,02912,NG,01,NG,0000004` | 残留帧继续串位 |

**串位方向演示（对应"NG→OK"场景）**：

```
拍 A（实判 OK）→ T2 回帧 RT,xxxx,OK 滞留/未及时被取走
拍 B（实判 NG）→ 上位机发 T2 → 读到的却是拍 A 的那条 RT,...,OK 残留帧
              → ParseResult 看到 OK → 写 PLC 1(OK)　← NG 被放行！
拍 B 真正的 NG 帧       → 留到下一次读取被消费，错位继续滚雪球
```

正常配对的点位（日志中大多数）NG 都正确写 2，解析本身没错；**错在"响应流与指令流对不上"**。

## 三、根因分析

### 1. 直接根因：`SendCommandAndReadLine` 不做"响应↔指令"匹配

`KeyenceIV4Camera.SendCommandAndReadLine`（KeyenceIV4Camera.cs:283）的逻辑是：

```csharp
_stream.Write(指令 + "\r");
... 逐字节读一行，读到的就是返回值
return line;    // 不校验这一行是不是本条指令的应答
```

调用方（T2/PW/OF/PR/T1）各自拿到这一行后**凭内容前缀做自己的判断**——例如：

- `TriggerAndRead` → `ParseResult` 只检查前缀是不是 `RT,`，是就按判定解析；
- `SwitchProgram` 只检查前缀 `PW` 或 `ER,PW`。

**缺陷**：TCP 流按帧到达，基恩士无协议通信又无"命令序号/应答配对"机制。
当相机处理慢（T2 判定窗口 200ms~数秒不等）、上位机节拍较快时，
上位机发出本条指令后，流里还躺着上一条指令的应答帧，
`Read` 把旧帧当本条响应用掉，真正的本条帧又被压到下一次读取——错位形成。

### 2. 放大条件（日志里上相机 213 尤甚）

- 相机**响应时序不稳定**：日志中 T2 从 200ms 到 5s 无响应再到断线重连都有；
- **PW/T2 交替发送**：每条指令都要求一条独立应答，任何一条应答晚到，后面全部前移一位；
- 相机连接偶发中断重连（18:26 时段多次"通讯中断→重连"），重连后旧连接残留帧与新连接状态叠加。

### 3. 解析层的第二个隐患：详细格式只看第 2 个字段

现场实测详细格式为 `RT,计数,判定1,01,判定2,数值`（如 `RT,02765,NG,01,NG,0000000`），
当前 `ParseResult`（KeyenceIV4Camera.cs:485-492）只认 `fields[1]`（判定1）。
日志里 `fields[1] == fields[3]` 恰好一致，但一旦现场某程序里两个判定字段不一致
（理论上可配置出"工具 A OK、工具 B NG"的复合判定），只取第 2 个字段仍可能漏 NG。
**这只是纵深防御问题，不是本次现象的主因**（主因是错位）。

## 四、修复方案

改动范围：`CommandCenter/Services/KeyenceIV4Camera.cs` 一个文件。
不改协调器、不改 PLC、不改相机协议/指令内容，对现场行为无协议层影响。

### 方案 1：发指令前吞掉输入缓冲中的残留帧（治本第一层）

在 `SendCommandAndReadLine` 发送指令之前，**先非阻塞排空 `_stream` 已缓冲的可读字节**：

```csharp
// 发送指令前先排空输入缓冲残留（上一拍未取走的旧应答帧），
// 保证本行 Read 到的第一条应答就是本条指令的应答。
while (_stream.DataAvailable)
{
    var tmp = new byte[512];
    int n = _stream.Read(tmp, 0, tmp.Length);
    if (n <= 0) break;
}
```

要点：
- `DataAvailable==false` 时立即跳过，**不等待**、不阻塞（对慢相机无副作用）；
- 排空只发生在"流里已有旧数据"时，正常情况下上层只发指令、等自己的应答，不会多读；
- 配合方案 2 的"读不到就判失败"，排空不会吞掉当前指令的应答。

### 方案 2：按指令类型校验应答前缀，不是本指令的应答就继续读（治本第二层）

给 `SendCommandAndReadLine` 增加期望前缀集合参数；读到的行若前缀不匹配，**丢弃并继续读**，
直到读到匹配前缀、或超时，或读到 `ER` 错误帧：

```csharp
// 每条指令期望的应答前缀：
//   T2/RT → "RT", "ER"（判定帧 / 错误帧）
//   PW    → "PW", "ER"
//   OF    → "OF", "ER"
//   PR    → "PR", "ER"
//   T1    → "T1", "ER"（仅触发场景，收到回显即可）
private string SendCommandAndReadLine(string command, int readTimeoutMs, string[] expectedPrefixes)
{
    ... 发送指令 ...
    while (有读超时兜底)
    {
        读一行 line;
        if (line 以任一期望前缀开头) return line;   // 是本次指令的应答 → 返回
        丢弃继续读;                                  // 残留帧 → 跳过，不误用
    }
    return null;  // 超时：MarkDisconnected，重连后重试
}
```

调用点全部传入对应的期望前缀：
- `TriggerAndRead` → `new[] { "RT", "ER" }`；
- `SwitchProgram` → `new[] { "PW", "ER" }`；
- `SetOutputFormat` → `new[] { "OF", "ER" }`；
- `ReadProgramNo` → `new[] { "PR", "ER" }`；
- `SendTrigger` → `new[] { "T1", "ER" }`。

行为变化：
- **变好**：T2 读到残留 `PW`，现在会跳过、继续等真正的 `RT,...`，不再"响应格式异常"误判；
- **保护**：读不到匹配帧（相机真无应答）→ 仍走既有 `MarkDisconnected` + 返回失败，
  与现在"相机无响应 → NG"的行为一致，不会因加了匹配而出现"静默放行"的空窗。

### 方案 3：`ParseResult` 详细格式下"任一判定字段为 NG 即 NG"（纵深防御）

详细格式不再只看 `fields[1]`，而是遍历响应中**所有明文 `OK`/`NG` 字段**：

```csharp
// 详细格式：字段≥2 时，扫描所有字段统计明文判定——
//   * 任何一个字段是 NG → 保守判 NG（复合判定任一工具不良即不良，绝不放行）
//   * 没有 NG 且存在至少一个 OK → 判 OK
//   * 没有任何明文 OK/NG（如全是数字位图）→ 回退标准格式逐位判定
bool anyNg = false, anyOk = false;
foreach (var f in fields)
{
    var t = f.Trim();
    if (t.Equals("NG", OrdinalIgnoreCase)) anyNg = true;
    else if (t.Equals("OK", OrdinalIgnoreCase)) anyOk = true;
}
if (anyNg)  return NgResult(...);
if (anyOk)  return OkResult(...);
// 否则回退标准格式（原逻辑）
```

与 V2.14.10 的兼容性：
- 标准格式 `RT,00000000`（纯位图）没有任何明文 OK/NG → 仍走逐位判定，行为不变；
- 详细格式 `RT,计数,OK,01,OK,数值` → 有 OK 无 NG → OK（不变）；
- 详细格式 `RT,计数,NG,01,NG,数值` → 命中 NG → NG（不变）；
- **新增**：万一出现 `RT,计数,OK,01,NG,数值`（工具判定不一致）→ 判 NG，放行风险被堵死。

### 不改动项（评审确认范围）

- **不改** `ProductionCoordinator` 的"判定即写"时序（V2.13.7 定稿，非本次问题）；
- **不改** PLC/相机指令内容与协议（只动上位机内部的"读应答"逻辑）；
- **不改** `ReadImage`（BR 二进制取图是精确按长度读字节，与行配对无关）。

## 六、风险与回滚

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| `ER` 前缀被误当残留丢弃 | 若期望前缀集合漏了 `ER`，真实错误帧会被跳过→ 永远等不到应答→超时判失败（偏保守 NG，不至于放行，但会误伤） | 五.3 静态走查必查；所有集合统一含 `"ER"` |
| 排空误吞当前指令应答 | 若相机应答先于"排空"到达（DataAvailable 含真应答） | 实际不可能：排空发生在**发送指令之前**，此时流里只可能有旧残留；发送后应答才会到来 |
| 读超时仍判失败 | 相机真无应答时行为与现状一致（NG+重连），不放行 | 无新增风险 |
| 详细格式字段位置再变化 | 新格式不含明文 OK/NG → 回退标准格式逐位判定，保守 NG 兜底 | 不引入新误判 |

**回滚**：本次只改 `KeyenceIV4Camera.cs` 单个文件，改动局部（一个私有方法 + 5 个调用点的参数 + ParseResult 一段），
git 回退该文件即可，无数据/配置迁移。

### 与方案的差异（实施时按实际情况微调）

1. 方案原文在调用点用"按指令名取前缀"（如触发用指令名 `T2`），实施时改为**按指令的应答前缀固定传参**
   （T2/RT 指令应答一律 `RT` 开头，故 `TriggerAndRead` 传 `RT`+`ER` 而非指令名），更贴合实际回帧，
   `T1` 触发用回显指令名本身。含义等价、更准确。
2. 排空实现增加了 `n <= 0` 保护（读失败即停止排空），其余与方案一致。
3. 前缀匹配用 `StartsWith` + `OrdinalIgnoreCase`，且刻意**不用精确指令名长度限定**——
   防止相机在 `RT`/`PW` 后附加可变尾巴时被误判为残留。

## 九、补充排查归档（2026-08-15 晚）："改了扫码后相机疯狂触发/搜不到NG"的因果结论

> 客户反馈"改了扫码枪逻辑后，相机疯狂触发、上位机搜不到 NG"疑似强相关。本结论来自代码审查 +
> `运行日志_20260815.log` 逐条核对，归档以防客户/后续排查误判方向。

### 结论：相机疯狂触发与扫码枪逻辑**无原因关系**（时间上巧合，非因果）

### 证据一：代码层面扫码枪与相机触发完全隔离

| 对象 | 连接目标 | 指令 | 作用域 |
| --- | --- | --- | --- |
| 扫码枪 `ScannerTcpService` | `19.87.6.100:9004` | 仅 `LON`（开激光）、读条码 | 只影响序列号接收 |
| 相机 `KeyenceIV4Camera` | `19.87.6.213/212:8500` | `PW/T2/RT` | 只发拍照指令 |

两者端口、IP、指令、TcpClient 全部独立，无共享连接；
协调器内扫码通道与相机通道是两个独立状态机，扫码改动（V2.14.30 失败过滤 /
V2.14.32 弹窗 / V2.14.33 死等补录）只影响 `_serialErrorSeen/_serialReceived` 标志与 40004 结果，
**无任何路径触发相机**。

### 证据二：日志里相机触发计数大跳变 = 存在"第二触发源"

上位机每发一次 T2，相机 RT 触发计数只 +1；而日志出现与上位机动作无关的跳变：

| 时间 | 点位 | RT 触发计数 | 相对上一拍跳变 |
| --- | --- | --- | --- |
| 19:03:08~19:03:50 | 点位1~11 | 03271→03281 | 严格 +1（上位机正常触发） |
| 19:03:56 | 点位12 | 03291 | **+10** |
| 19:04:10 | 点位14 | 03375 | **12 秒内 +84** |
| 19:04:27 | 点位16 | 03457 | **+76** |
| 19:05:14→19:05:33 | 点位23→26 | 03475→03634 | **+159** |

单点 T2 只会 +1；+10/+84/+76/+159 的大跳变只能来自**周期性高频的第三方触发**
（约每秒 9~10 次），候选：相机 IV Navigator 被误设为定时/连续拍照、PLC/硬件 I/O 硬触发、
另有程序连相机触发。**与扫码枪无关，与上位机无关，需现场停掉该源验证。**

### 证据三："搜不到 NG"是同一根因的连锁反应

第二触发源把触发计数顶高 → 取图按"目录修改时间最新"取到别的枪的旧图
（现场点位14 取到 `00356`，落后本枪 ≈18 张）→ 显示/归档图与判定错配。
V2.14.34（应答配对）与 V2.14.37（取图事件路径优先）为上位机侧缓解，根因仍是多出的触发源。

### 现场排查清单

1. **先确认"改了扫码"具体指什么**：扫码枪 IP/模式配置、PLC 梯形图，还是仅测试窗体的手动操作？
   若只是 V2.14.30~33 程序逻辑改版，与本问题无关；
2. **查相机 IV Navigator 触发方式**：是否被误设为 **定时/连续拍摄** 或外部输入触发
   （短间隔自动拍，正是 +84/+76/+159 的来源）；
3. **断开第二触发源复测**：停掉其余连相机的软件 / 拔掉相机外部触发线，确认日志 RT 计数恢复
   "每次 +1"；恢复 +1 后判定、取图、存图自然对齐。

### 状态

本文档原"NG 被报成 OK"结论（第三~八部分）仍成立；本部分为新增的因果排除结论，与 V2.14.34 修复不冲突。
